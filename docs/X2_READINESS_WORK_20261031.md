## “部署后自动到准备姿态”的接口边界

模型文件已在机器人上，不等于电机闭环已启动。11500 导出只计算策略动作，没有独立的慢速准备状态机。现有 SDK 独立部署示例 `motion_control_node.cc` 也明确区分 `JointDefault()` 的实测姿态插值与 `RlDefault()` 策略推理；不能把模型加载当成准备动作。

正确的独立执行顺序是：原生 MC 关闭 → 从新鲜实测姿态缓慢准备 → 到位/速度/身体姿态检查 → 连续真实观测历史 → 连续交接到 11500。准备由程序发送电机命令完成，不要求用户手动掰关节。未通过准备和接管时，不直接从自然下垂姿态发布 11500 输出。

本轮继续修复只读探针的采样问题：原子状态已按 50 Hz 发布，原探针又使用独立 50 Hz 定时器，二者相位与抖动会跳过样本、重置历史。改为每收到一条新状态处理一次，仍保留真实时间戳、50 ms 陈旧门限及 30 ms 历史间隔检查，不补造历史。

机载 `stream-event-core5-60s-r1` 实测 60.03 秒收到 2952 条状态，得到 2274 个完整历史推理帧（此前独立定时版本 1445 帧/60 秒；不同时间窗，不能视为严格匹配性能对照）。推理 P99 4.77 ms，整体处理 P99 10.75 ms；仍有 53 次历史间隔超 30 ms、45 次陈旧/未来数据拒绝和 8 次流暂停/陈旧重置。最慢处理 79.57 ms，其中同步记录文件耗时 73.79 ms，确认同步日志是剩余阻塞来源之一。没有放宽门限，仍未通过连续接管；没有启用电机输出。实时记录隔离与上游真实采样间隔还需继续处理。

当前 `ready_for_hardware_trial=false`。尚未启用自定义策略电机输出或完成控制接管；上面的原生 MC 模式请求确已执行，不能写成整轮“未改变机器人模式”。

## 支撑假设实验的结果与适用范围

以下都不是当前实机条件的验收：

- 放宽 **仿真** 接管倾角到 0.26 rad 的反事实对照中，“先接管再卸载”虽末段站稳，交接和早期控制出现最高约 666 N 自碰撞；全程保持承重吊挂也持续摆动。不能仅凭没有提前终止或末段站稳判成功。
- 5 秒同步交接/卸载，末段 30 秒未倒，但交接阶段倾角最高约 32.6°、角速度 5.21 rad/s、力矩饱和、自碰撞最高约 773 N，仍失败。主要碰撞为 pelvis 与 hip_roll_link。
- 1 秒交接配 1/3/5 秒卸载，均有交接自碰撞（约 619/139/138 N）及力矩饱和；没有可发布到实机的通过项。
- 单独把准备增益改为策略增益，没有消除交接后的碰撞（最高约 615 N）；不能将增益差异直接写成已解决的根因。
- 基于模型 COM/吊点关系的腰部姿态候选，在 16.12 秒触发倾角/高度门限，未接管。它同样依赖旧吊挂假设，不继续用作当前实机方案。

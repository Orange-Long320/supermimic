# 原生频率 IMU 积分对照（2026-11-02）

用户要求把回放积分从 50 Hz 控制帧快照改为躯干 IMU 原生频率，并实测差别。范围仅官方仿真、离线积分与只读记录；没有策略训练、没有实机、没有电机命令。

## 动机与链路确认

`scripts/deploy/official_sim_state.py` 的实现在 `on_imu` 中只保存**最新一条** IMU 消息，再由 20 ms 定时器整体转发；策略侧每个控制帧读到的就是"该 tick 之前最新的一条"。因此部署链路里积分器看到的是 50 Hz 抽样，而不是传感器原始序列。

本次新增两个入口，均不发布 ROS 话题：

- `scripts/deploy/record_sim_native_imu.py`：直接订阅 `/aima/hal/imu/torso/state`、`/aima/hal/odom/state` 与四组关节，逐条落盘，同时记录消息头时间与本地接收时间；深度 400 的 BEST_EFFORT 队列，避免记录器自身丢样影响对照。
- `scripts/evaluation/eval_native_rate_imu.py`：同一份记录上做两路积分。A 用全部原生样本和各段自身 dt；B 模拟现有链路，只在 20 ms tick 上取"该 tick 之前最新的一条"，两者都用梯形积分并与仿真里程计真值比较。

真值只用于评测，不进入任何一路积分。

## 单场次实测

同日程（stand/walk/stand/jog/stand/backward/stand/左转/stand/右转/stand）、同一固定 11500 导出策略与同一收步参考。会话 16:42:33–16:44:33，exit 0，策略记录 2826 帧 / 56.59 秒控制；load average 由 10.26 升到 13.99。

记录侧：躯干 IMU **500.04 Hz**、36000 条，间隔 p50 1.9999 ms、p99 2.0566 ms、最大 6.9766 ms、超过 20 ms 的间隔 0 次；里程计同为 500.04 Hz。原生的 500 Hz 与实机躯干 IMU 的 502.9 Hz 同量级。

| 项目 | 数值 |
| --- | --- |
| 对照时长 | 71.0 s |
| 真值 XY 路径 / 净位移 | 8.25 / 3.14 m |
| **原生 500 Hz 积分末端误差** | **3.98 m**（p50 1.69、p95 3.74） |
| **50 Hz 快照积分末端误差** | **37.09 m**（p50 17.89、p95 35.73） |
| 两者末端位置差 | 31.78 m（p50 15.23） |
| 原始加速度模长 p50 / p99 / max | 9.81 / 14.86 / **76.20 m/s²** |

历史 2026-10-31 那次 50 Hz 记录给出 58.8 秒末端 35.84 m，与本次快照变体的 37.09 m 同量级，说明该变体复现了既有链路的行为，不是新引入的实现差异。

## 差异来源

- 两路积分的时间平均速度差为 `[+0.441, +0.012, -0.153] m/s`，末端速度差 `[+0.297, +0.013, -0.084] m/s`。位置差 31.78 m 基本等于该速度差对时间的积分，是**持续同向的速度偏移**，不是随机游走。
- 快照端只保留冲击速度增量的一部分：以原生 `|a_world| > 15 m/s²` 的 11 个冲击峰计，投影保留比 p50 0.706、p05 0.254；按原始比力统计的 64 个峰，峰值幅度保留 p50 0.956、p05 0.573。
- 仿真的落地瞬态峰值达 7.8 g，20 ms 的梯形积分无法表示这种宽度只有几毫秒的冲击。**结论应表述为"50 Hz 抽样系统性丢失高频速度增量"，具体符号与幅度只在本场次测得，不据此断言对任意步态恒定。**

## 边界与未验证

- 仅一次确定性轨迹，且负载在 10.3–14.0 之间波动；需要重复场次才能把 3.98 m 当成稳定数字。
- 只做纯 strapdown，不含支撑脚零速修正、不含接触模型；**3.98 m 仍大于真值净位移 3.14 m，不能作为绝对位置来源**。
- 仿真 IMU 的姿态接近真值；实机姿态本身有误差，绝对数值会不同，方向性结论（原生频率显著优于 50 Hz 抽样）尚待机载只读验证。
- 未测量接触力，未接入控制回路，不代表策略行为或安全性。

## 在原生频率记录上重跑支撑融合：未获得改善

用 `scripts/evaluation/eval_native_rate_fusion.py` 把既有的 contact_jac + 自适应防滑滤波器接到同一场次的原生记录上。算法与测量噪声不变，只为保持"只改采样率"这一前提，把三处隐含绑定 20 ms 的常量改成物理量：足速低通的**时间常数**、支撑最短驻留的**秒数**、过程噪声按 dt 缩放。

| 变体 | 末端误差 | 最大 | p50 | 接受的更新数 |
| --- | ---: | ---: | ---: | ---: |
| 原生 500 Hz（积分与更新都在原生频率） | 2.362 m | 2.381 | 1.751 | 24021 |
| 20 ms 几何 + 50 Hz 传播（原始管线） | **0.877 m** | 1.882 | 0.652 | 2371 |
| 原生几何抽样到 50 Hz + 50 Hz 传播 | 0.473 m | 2.048 | 0.473 | 2362 |
| 原生预积分 + 50 Hz 更新（原生几何） | 0.974 m | 3.018 | 0.725 | 2417 |
| 原生预积分 + 50 Hz 几何 | 1.277 m | 2.977 | 0.894 | 2385 |
| 原生 + 按 dt 缩放测量噪声 | 1608 m | — | — | 194 |

**结论：原生频率没有改善融合，反而在该场次退化到 0.877 m 基线的约 2.7 倍。**

- 上一步纯 strapdown 的 3.98 → 37.09 m 改善（约 9 倍）**没有传导到融合**。融合精度由接触速度测量主导，而该测量是关节运动学代理，不是接触力；原生频率把落地冲击瞬态原样带进来，2 ms 一次的高频更新又把时间上高度相关的测量误差当成独立信息重复使用（接受更新从 2362 次升到 24021 次），滤波器被推偏。
- 把更新率与积分率解耦（原生预积分 + 50 Hz 更新）仍未超过基线（0.974 / 1.277 对 0.877）。因此这一场景的瓶颈是**接触代理质量**，不是传播精度。
- 按 dt 缩放测量噪声的变体只剩 194 次更新、滤波器基本失效，属于失败对照，仅用于说明该方向不成立。
- 原生几何抽样到 50 Hz 得到 0.473 m，与原始管线 0.877 m 的差异来自不同的足速平滑路径，单场次内不足以宣称改善。

边界：单场次、同一确定性轨迹、负载 10.3–14.0；关节样本只有本地接收时间，未记录消息头时间戳，因此关节与 IMU 的对齐依赖接收时刻；支撑仍是几何代理，没有测力；离线回放，不接控制。

证据：`native-fusion-r3.json`（六变体）、`native-fusion-r1.json`、`native-fusion-r2.json`（中间版本）；脚本 `scripts/evaluation/eval_native_rate_fusion.py`。

## 力矩接触代理：当前数据无法执行，未得到末端误差

目标是用关节力矩估计替掉几何接触代理。检查前提时发现仿真**不发布关节力矩**，因此该实验在本环境不能运行，没有可报告的新误差数字。

两处独立证据：

- 新增记录器在第二场次（`native-r2-record/joints.jsonl`，185325 条组快照）中，第 4 字段 effort **非零条目数为 0**。
- 策略自身的 `native-r1/policy/frames.jsonl` 2826 帧全部带 `joint_effort` 字段，`max|joint_effort| = 0.0`、非零占比 0。

`official_sim_state.py` 的 `efforts` 字段与 `official_sim_policy.py` 的 `invalid simulator effort sample` 检查都只能证明字段存在且有限，不能证明其数值有意义；仓库里 `audit_stand_entry_pair.py` 已记录过"joint effort 字段可能未填充，不得据此推断零力矩或零负载"。

已实现的代码路径（`eval_native_rate_fusion.py --contact-source torque`）：对该侧腿关节求解 `J^T F = tau` 的最小二乘解，取世界 z 分量作为准静态支撑力，门限按体重比例（默认 0.1 倍体重），符号约定由静止段的实测中位数自动判定并写入报告。**当记录中的 effort 全为零时程序直接报错退出**，避免把"零力矩→无接触→退化为纯 strapdown"误读成融合结果。

实机上可能的替代来源：`/aima/hal/joint/norealtime/{udcu,ddcu}_joint/state` 提供 `motor_current_state` 与 `target_effort` 原始整数（见 `scripts/deploy/read_x2_hardware_status.py`）。这是非实时话题，发布速率与实际可用性尚未测量，且需要与关节力矩的比例/零点核对，不能直接当作接触力使用。
